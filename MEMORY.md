## Patrones detectados

- **websockets v17+ API change**: `websockets.serve()` ahora requiere `async with` pattern, no `run_until_complete`. Usar `asyncio.new_event_loop()` en thread separado con `asyncio.Future()` para mantener vivo el loop.
- **WebSocket server en gesturecontrol**: LandmarkServer corre en thread separado con asyncio loop propio. `publish()` usa `run_coroutine_threadsafe()` para enviar desde el thread principal.
- **opencode en Omarchy = binario OFICIAL V2 (unico dueno)**: hoy corre OpenCode 2 en `~/.opencode/bin/opencode` (v2.0.28, instalado con `https://opencode.ai/v2/install`; metodo versionado en `linux/bin/opencode-install`). NO se instala por mise: el backend aqua da 404 en las releases 2.0.x (la 2.0 no se publica como GitHub releases de `anomalyco/opencode`). El lanzador `linux/bin/opencode` hace `exec "$HOME/.opencode/bin/opencode" "$@"`. Nada de pacman `opencode-bin` ni npm global `opencode-ai`. El binario V1 (aqua `1.19.0` en `~/.local/share/mise/installs/opencode/1.19.0/opencode`) se conserva SOLO como rollback y como binario de las sillas V1 mientras rig se adapta.
- **V2 trae servidor de fondo**: `opencode service` (start/restart/status/stop) mantiene un servicio caliente (p.ej. http://127.0.0.1:49374) y la TUI se conecta a el -> el arranque percibido baja de ~3.9s (V1, cold start por TUI) a ~0.1-0.5s (`opencode session list`). El archivo de servicio es `~/.local/state/opencode/service.json` (contiene un password: NO versionar).
- **Next.js 16: un solo `next dev` por arbol**: el segundo `next dev` en el mismo directorio falla con `Another next dev server is already running` (deja log/PID en `.next/dev/`). En cambio `next dev` (que escribe en `.next/dev/`) y `next build`/`next start` (en `.next/BUILD_ID`) CONVIVEN en el mismo arbol. Por eso agentes-platform main se sirve con build+`next start` (convive con el `next dev` del usuario en :3020) y el worktree `developing` (dedicado) con `next dev`.
- **pnpm 12 `ERR_PNPM_IGNORED_BUILDS`**: `strictDepBuilds` (default true) falla si hay build scripts sin revisar. En 12.4.2 solo `strictDepBuilds: false` en `pnpm-workspace.yaml` lo baja a warning; NO funcionan `--config.strictDepBuilds=false`, `--config.strict-dep-builds=false`, `.npmrc` (kebab o camel) ni `npm_config_*`. `allowBuilds` con valores string placeholder ("set this to true or false") NO aprueba nada. El install IGUAL enlaza `node_modules` antes de abortar, asi que el error deja las deps usables.

## Errores comunes y soluciones

- **gesturecontrol engine camera busy**: Proceso zombie retenía /dev/video0. Kill manual resolvió.
- **websockets RuntimeError: no running event loop**: API v17 cambió. Solución: `asyncio.new_event_loop()` + `run_until_complete(asyncio.Future())`.
- **El cursor se esconde solo cuando queda quieto**: no era inactividad de Hyprland (`cursor:inactive_timeout` ya valía 0) ni `hide_on_key_press`/`hide_on_touch`. La causa era **kitty**: `mouse_hide_wait 3` en `linux/config/kitty/kitty.conf` oculta el puntero a los 3 s de no moverlo **sobre la ventana de kitty** y lo muestra al mover; como las terminales cubrían la pantalla, parecía global. Fix: `mouse_hide_wait 0` + `omarchy restart terminal` (kitty recarga con SIGUSR1). Verificación: `scripts/verify/cursor.sh` y prueba visual: con el puntero sobre la barra (fuera de kitty) el cursor ya persistía antes del fix; sobre kitty, después del fix persiste 8 s+.
- **Nautilus "no abre" (Files)**: el servicio D-Bus `dbus-:1.1-org.gnome.Nautilus@0.service` (`nautilus --gapplication-service`) se queda wedged → `gtk-launch org.gnome.Nautilus.desktop` retorna exit 0 pero no crea ventana. Diagnóstico: `systemctl --user status 'dbus-:1.1-org.gnome.Nautilus@0.service'` (RSS >1GB, decenas de tasks) + `coredumpctl list | grep nautilus`. Fix: `pkill -x nautilus` (el servicio D-Bus lo relanza limpio en el próximo launch). Causa raíz: fuga de thumbnailers glycin (`glycin-image-rs` en bwrap) que nunca salen y revientan el proceso con SEGV. Si reaparece: limpiar bwrap huérfanos y considerar desactivar thumbnails nautilus.
- **opencode lentísimo al arrancar (>25s, cuelga)**: causa = `mise use -g --quiet opencode` dentro del lanzador (golpea el registro/red en cada arranque). Fix: fijar `opencode = "1.19.0"` en la config de mise y ejecutar `mise x opencode@1.19.0 -- opencode` (overhead ~0.02s; el binario aqua tarda ~0.70s por sí solo).
- **Backend npm de mise no corre postinstall**: `mise exec -- opencode` falla con `opencode-ai's postinstall script was not run`; el empaquetador (aube) ignora scripts. Evitarlo usando el backend aqua. Si se insiste en npm: `cd .../node_modules/opencode-ai && node postinstall.mjs`.
- **`pkill -f '<patrón>'` se auto-matchea** y mata la propia shell si el patrón aparece en el comando (p.ej. `pkill -f 'mise use'`). Filtrar por PID.
- **`grep` en la shell de opencode resuelve a BusyBox** (no soporta `-A`/`-B`): usar `/usr/bin/grep`.
- **hostname drift NixOS→Omarchy**: los hostnames pasaron a `laptopmarchy`/`astradeux`; cualquier script con `case "$(hostname)" in laptop|desktop)` queda muerto. Usar `scripts/detect-machine.sh` (hardware) o `~/.config/machine-type`. Corregido en `kvm-ensure.sh`.
- **`ip` de la shell del agente es BusyBox** (`~/bin/ip` → busybox, no soporta `-br`): usar `/usr/bin/ip`. Los scripts de sistema fijan `PATH=/usr/local/bin:/usr/bin:/bin:...` y usan iproute2 real.
- **ntfs3 rw en partición Windows**: si Windows usa Fast Startup, `mount -t ntfs3 -o rw` falla con `volume is dirty and "force" flag is not set!`. NO forzar; correr el setup desde Windows.
- **API de plugins V2: los plugins V1 NO corren**: V2 falla con `failed to load plugin ... PluginModule.LoadError: Plugin must export a default definition with an id and an effect or setup function`. Forma V2: `import { Plugin } from "@opencode/plugin"` + `export default Plugin.define({ id, async setup(ctx) { await ctx.tool.hook("execute.before"|"execute.after", (event) => {...}) } })` (el callback recibe UN evento mutable). Los args del tool estan en `event.input` (ya no `output.args`); para que el modelo vea texto hay que agregarlo a `event.result.content` y marcar `event.result.metadata.<flag>`. NO usar el helper `$` de Bun (V2 no lo provee): usar `spawnSync` de `node:child_process`. La clave de config es `plugins` (plural) y los plugins locales se autodescubren desde `~/.config/opencode/plugins/` (y `plugin/` singular).
- **`~/.config/opencode` es symlink -> el watcher de V2 falla**: V2 loguea `ERROR failed to subscribe ... inotify_add_watch on '/home/eztvn/.config/opencode' failed: Not a directory`. V2 igual funciona, pero el hot-reload de config no existe: hay que `opencode service restart`.
- **V2 no acepta `opencode --agent X --model Y`**: esos flags solo existen en `opencode run` (top-level solo hay `--prompt`, `--standalone`, `--server`, `--auto`, `-c/--continue`, `-s/--session`). Por eso `rig spawn` (que lanza `opencode --agent ... --model ...`) falla con `cli process failed cause=ShowHelp` (ticket #98 RIG-LAUNCH-FIABLE).
- **`/tmp` es tmpfs chico (~1.5G libres)**: para instalaciones/descargas grandes usar `TMPDIR=/var/tmp`.
- **Leer archivos bajo `~/.config/opencode/` con la tool `read` re-inyecta TODO el AGENTS.md (~60 KB)**: usar `bash cat` para inspeccionarlos.
- **`ERR_PNPM_IGNORED_BUILDS` al instalar agentes-platform (`@google/genai`, `protobufjs`)**: ver patron de pnpm 12. Un install que escupe ese error deja `node_modules` poblado (el linking corre antes del check); el wrapper lo tolera comprobando que `node_modules` existe.
